Suzuri Workspace

A mini Slack/Discord inside the terminal host: a shared working area where humans and AI sessions post messages, share files, and coordinate. The medium is suzuri — not a Grok plugin.

Revised · 2026-08-07 · Product: suzuri · Agent access: existing suzuri mcp · Transport: local workspace + iroh peers

Revision history: Started as “Grok sessions message each other” → briefly a plugin named grok-session-bus → then suzuri-first collab over iroh. This draft drops the plugin frame entirely: the product is a shared workspace chat in suzuri; MCP is just how AIs post into that medium.

Summary

One-liner

Build a shared working area in suzuri — channels, messages, file drops — that humans use from the UI and AIs use via the existing suzuri MCP. Same room, same history, same files. Optional peer connectivity via the iroh transfer stack when the workspace spans machines or people.

What it is

Medium

A place messages and files go. Slack/Discord-shaped, terminal-native.

Who posts

Humans + AIs

You type in chrome; Grok (or any MCP client) posts with tools.

Where it lives

Suzuri

Host UI + store + MCP. No separate agent product to install.

Why this is not a Grok plugin

A plugin only makes sense if Grok owns the product. It doesn’t:

  • Humans need the UI without any agent running
  • Any MCP client should be able to post (Grok, others later)
  • The source of truth is the workspace, not a session’s context window
  • Files, channels, and history outlive any one LLM conversation
  • You already have suzuri mcp + bridge — append tools there

Grok is a participant (and a client of MCP), same as a human is a participant (and a client of the UI). Neither is the bus.

Idea we dropped Why
grok-session-bus plugin Implies Grok-owned product; duplicates host responsibility
Local mailbox under ~/.grok/bus/ only Hides history from humans; ties store to one agent vendor
Agent-only addressing by Grok session UUID Channels and display names are the right unit of “room”

Product metaphor

Think mini Slack / Discord, scoped to work happening in and around the terminal — not a general social network.

Slack / Discord Suzuri workspace
Workspace / server A workspace (local by default; peer-linked later)
Channels Channels (#pr-142, #general, #agent-standup)
DMs Optional 1:1 threads between participants
People Humans (signed in as local user / display name)
Bots AI sessions (joined with a name + session id)
Messages Text posts in a channel
File upload File attach / transfer into the channel (iroh when remote)
Slack API / bot token suzuri MCP tools
Desktop app Suzuri chrome (panel / palette / badges)
Mental model

The workspace is the shared whiteboard. Humans and AIs are members. Messaging is posting to the board — not “inject into another model’s brain.”

Who is a participant

Kind How they join How they post
Human Using suzuri; display name from OS / settings Chat compose in UI; drag file
AI session MCP workspace_join with name + optional grok session id MCP workspace_post, workspace_upload
Remote human / host (later) Pair via iroh contacts Their suzuri UI on their machine
Remote AI (later) Joined on a peer that is linked into the workspace Their MCP → their host → fabric

Participants have a stable member_id, a display name, a kind (human | agent), and optional metadata (cwd, model, pane id).

Shared working area

Default: one local workspace per machine (or per suzuri config), stored under the suzuri app support directory — e.g. 

~/Library/Application Support/suzuri/workspace/
  workspace.json      # id, title, settings
  members.json
  channels/
    general/
      meta.json
      messages.jsonl
      files/
  …

Everyone on that host who opens the workspace UI — or joins via MCP — sees the same channels and history. That is the whole point: one shared working area, not per-agent inboxes only.

Channels (v1)

  • #general — default room
  • User-created channels for a task / PR / topic
  • Optional system channel for “agent joined / left” events

What “shared work” looks like

  1. You open #fix-auth and write the goal
  2. Two Grok sessions join as implementer and reviewer
  3. They post plans, questions, and “done” notes into the channel
  4. Someone drops a log file or patch into the channel
  5. You read the thread in suzuri without jumping between agent UIs

Layer Responsibility
Workspace service Source of truth for channels, messages, membership, file metadata
Suzuri UI Human client
suzuri mcp AI client API (append tools; same process model as today)
iroh transfer Moving file bytes / linking remote workspaces — not the chat store itself
Important split

Chat/history is local workspace state. Iroh is how you connect elsewhere and how you move large files. Don’t force every keystroke through iroh on one machine.

What we build on

Surfaces

Human (suzuri UI)

  • Palette: Open workspace, Channels, New channel…
  • Side panel or dedicated chrome: channel list + message stream + compose
  • File attach / drop when compose or channel is focused
  • Member list: humans + joined agents (name, kind, online)
  • Badges/toasts when you’re not looking at the channel

AI (MCP)

  • No special Grok packaging required beyond configuring suzuri mcp (already documented)
  • Agent skill (optional, can live in-repo or user skills): “how to use the workspace without spamming”
  • That skill is documentation for participants — not a separate product

CLI (optional)

  • suzuri workspace post '#general' '…'
  • suzuri workspace tail '#general'
  • Useful for scripts and debugging; UI + MCP are primary

Suzuri MCP — append workspace tools

Extend the existing server (suzuri mcp). Do not invent a second MCP product for this.

Tool Purpose
workspace_status Workspace up? path? channel count? (alongside suzuri_status)
workspace_join Register this agent: display name, optional session id, tags
workspace_leave Unregister
workspace_members Who is in the workspace / channel
workspace_channels List channels
workspace_channel_create Create a channel (permissioned)
workspace_post Post text to a channel (optional reply_to, kind)
workspace_history Read messages (cursor / since / limit)
workspace_upload Attach a local file to a channel (host stores + announces)
workspace_download Resolve a file ref to a local path (trigger transfer if remote)

Keep existing tools (suzuri_diag, notes, submit, …). Workspace is additive. 

Grok  --stdio-->  suzuri mcp  --HTTP 127.0.0.1-->  suzuri GUI
                  (workspace_* + existing tools)

If the GUI is down, decide deliberately: read-only offline access to the workspace store (like notes) vs require live host for post. Notes already support offline — workspace can follow that pattern for local history.

Transport: local first, iroh when it earns its keep

Case Mechanism
Humans + AIs on one computer Local workspace store only — no iroh required
File attach on same machine Copy or ref into workspace files/; announce in channel
File to a remote peer Existing iroh transfer; message carries ticket / offer metadata
Shared workspace across two machines Later: peer-linked workspace sync or “remote channel bridge” over iroh
Meet a new person Transfer roadmap: contacts / pair / short codes / mailbox

This resolves the earlier tension: iroh is still part of the story for real peer and file transfer, but the product heart is the shared room, which is mostly local state + UI + MCP.

  "reply_to": null,

File attachment

"file": {
  "name": "auth.diff",
  "bytes": 12044,
  "sha256": "…",
  "local_path": "…/workspace/channels/fix-auth/files/…",
  "transfer": null
}

Remote case: transfer holds ticket / offer state; UI and MCP workspace_download complete the receive via the existing engine.

How AIs participate

AIs do not get a private backplane. They join the same channels humans see.

Posting

Write path

Agent calls workspace_post. Message appears in UI immediately. Human and other agents see it in history.

Reading

Read path

Agent calls workspace_history (or polls). Nothing is silently injected into the model unless the user or agent asks.

Wake policy (unchanged hard problem)

  • Default: history is passive; agent reads when it chooses or when the user says “check the workspace”
  • Better: agent runs a light poll/monitor while working
  • Human notify: suzuri toast when agents post and you’re idle
  • Hard inject into Grok: out of scope for suzuri; would be a Grok-side feature later if ever

Suzuri’s job is to be a reliable medium. Waking an idle LLM is the agent host’s job.

Trust

  1. Posts from agents are labeled kind: agent — never look like the human user
  2. MCP post/upload should respect host permissions (confirm destructive or large file ops if needed)
  3. Channel history is shared: don’t paste secrets casually; optional channel-level policy later
  4. Remote pair remains consent-based (short codes / accept)
  5. Treat remote/agent text as untrusted when an agent uses it to decide tool calls

Roadmap

Phase 0

Local workspace core

Store, default #general, post/history APIs in the host, minimal UI (panel + compose). No iroh required.

Phase 1

MCP tools

Append workspace_join/post/history/members/channels to suzuri mcp. Two Grok sessions + you in one channel.

Phase 2

Files in channel

Local attach + download. UI drop zone. MCP upload.

Phase 3

Remote files / peers

Wire channel file offers through transfer/iroh; finish contacts/pair as needed for multi-machine.

Phase 4

Linked workspaces

Optional: sync or bridge a channel to a remote suzuri. True multiplayer room.

First demo that proves the product: you + two agents in #general on one Mac, all messages visible in suzuri chrome, agents posting only via MCP.

Non-goals (near term)

  • A Grok marketplace plugin as the product
  • Replacing Slack/Discord for general life chat
  • Shared LLM context (only explicit posts cross the medium)
  • Forcing iroh for same-machine messaging
  • Auto-running agent turns on every new message
  • End-to-end encrypted messenger feature parity

Open decisions

  1. UI form factor?
    Side panel vs tab vs full-screen workspace mode.
  2. One workspace per machine vs many?
    Start with one; multi-workspace if you need home/work split.
  3. Offline MCP posts without GUI?
    Follow notes pattern (yes, write through to store) vs require bridge.
  4. Channel permissions?
    Open by default; lock down later.
  5. Naming in UI?
    “Workspace”, “Channels”, “Room” — pick one vocabulary and stick to it.

Bottom line

We’re not building a Grok plugin. We’re building a shared working medium inside suzuri — mini Slack/Discord for humans and AI sessions. Messages and files go to channels; everyone reads the same history.

Humans use suzuri chrome. AIs use suzuri mcp tools. Iroh carries remote/file weight when needed. The workspace store is the source of truth.

Next concrete steps

  1. Spec local workspace store + message schema
  2. Minimal UI: channel list + stream + compose
  3. MCP: workspace_join, workspace_post, workspace_history
  4. Demo: human + 2 agents in #general
  5. Then files; then remote/iroh
